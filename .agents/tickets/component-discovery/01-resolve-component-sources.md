# 01: Resolve component sources and enrich variant guidance

Status: in-progress
Blocked by: none

## Goal

Give agents verified component definition paths and available size/variant values in diagnostics by resolving direct imports, common project aliases, explicit barrel re-exports, and prepared Nuxt component mappings to Vue SFCs and reading a bounded set of prop declarations. Preserve selfix's existing enforcement and source-only API behavior.

This is one observable slice spanning import identity, source resolution, metadata extraction, diagnostic output, tests, and documentation. It does not introduce wrapper policy inheritance or general TypeScript evaluation.

## Acceptance criteria

- [x] Make automatic discovery from supported project metadata the normal CLI path. Provide optional project context for API callers; existing source-only calls do not start resolving component files. Use the CLI config directory as the project root unless explicitly overridden; keep path bases documented. Explicit aliases/component-to-file mappings are escape hatches that override discovered mappings, not required duplication of information available from supported metadata. Preserve existing `createLinter`/`lintSource` calls and synchronous `lint(source, filename)` behavior. Do not reinterpret the CSS `base`, `cssAliases`, or import-recognition `ui` prefixes as component source mappings.
- [x] Preserve imported export identity alongside the local name; resolve supported direct imports and explicit named/default barrel re-exports to `.vue` definitions. Define extension/index probing and cycle/ambiguity handling. Read common tsconfig/jsconfig path mappings and their supported extends chains, preserving each mapping's defining-directory base and matching precedence. Cover relative/direct aliases and explicit barrel exports; general package-condition resolution and export-star traversal remain deferred. Document unsupported resolution cases instead of guessing conventional alias targets.
- [x] Read literal `defineProps` types, `withDefaults`, and same-file prop/value type aliases and interfaces within an explicit supported subset. Only list complete, verified string values for size/variant props. Support direct members and same-file aliases/interfaces; inherited members, intersections/unions of whole prop objects, imported types, and factories may remain unsupported with metadata omitted. Literal unions on individual props are supported. Do not claim general TypeScript support.
- [x] Keep local component identity unchanged for contracts, `classProps`, and existing diagnostics. A renamed import or re-export must not silently switch its effective policy to the defining component's name.
- [x] Enrich applicable diagnostics with verified available values and a component definition reference. Preserve the original offending SFC location and existing `file`/`{{file}}` meaning. Use optional additive JSON metadata and corresponding text guidance for the definition file and known size/variant values. Keep existing placeholders unchanged; new placeholder syntax is not required. Keep component guidance distinct from spelling suggestions and source edits.
- [x] Treat discovered values as accepted prop choices, not proof that a particular variant visually replaces a rejected utility. Never attribute an unrelated factory or another component's props to the reported component, invent a value, or direct users to edit installed dependencies.
- [x] Unavailable metadata retains the original finding and useful general guidance. Distinguish unsupported optional metadata from broken inputs: retain general diagnostics when a valid source uses unsupported prop syntax; report malformed explicit configuration, missing explicit mapping targets, and unreadable/malformed discovered mapping artifacts actionably. Missing Nuxt preparation should explain the application-owned preparation command when Nuxt discovery is requested or established from project metadata; it must not masquerade as successful discovery. Existing parse errors, uncertainty diagnostics, and theme failures must not be suppressed.
- [x] Use a per-linter project snapshot: recreate the linter after component or project-metadata edits, and create a fresh snapshot for every CLI invocation. Document this lifecycle rather than adding a watcher or process-global cache. The caller-supplied SFC source remains authoritative over disk content; caches must not leak across unrelated projects or produce undocumented stale metadata after dependency edits.
- [x] Preserve Nuxt UI generated theme loading through `cssAliases`, application-owned preparation, missing-generated-file errors, and custom application tokens. Discovery does not execute Nuxt/Vite/app configuration or add Nuxt/UI runtime dependencies.
- [x] Preserve configured global/auto-imported U-component recognition and `ui` slot-map inspection even when no component source can be resolved. Keep original `prop`/`slot` context, classProps matching, and independent rule findings. Read static component mappings produced by application-owned Nuxt preparation to resolve auto-imported component definitions without manual entries for each U-component. Inspect the actual pinned generated artifact and parse only supported data/declarations; do not assume an artifact path or format before verification. Cover generated paths to installed sources, local component overrides and configured naming where represented by those mappings. Identifying a source does not automatically make an unsupported prop type readable or change recognition/classProps policy.
- [x] Extend the existing pinned Nuxt smoke fixture with an actual `UButton` and configured `ui` prop findings, including original locations and a corrected passing case. Verify automatic resolution of the actual prepared UButton source without an explicit component-file mapping. Also verify a prepared local auto-imported Vue component with readable size/variant props gets enriched guidance. Explicitly configure recognition and classProps; source discovery does not authorize policies based on component names. If UButton uses imported/factory types beyond the core subset, assert retained findings and absent unverified variant lists rather than pretending full Nuxt UI metadata extraction. Preserve the generated-theme-versus-package-fallback checks.
- [x] Document configuration, supported syntax/resolution, API compatibility, diagnostics, and Nuxt limits in the appropriate docs pages. Keep one package, one standalone config/runner, Vue/Tailwind-only consumer peers, and no application expression evaluation or autofix.

## Verification

Use test-first collector, public-linter, configuration, and CLI regressions with real Vue parsing and temporary files. Cover direct imports, renamed exports, multi-hop explicit barrels, tsconfig/jsconfig aliases and extends bases, explicit override precedence, different CLI working directories, cycles, ambiguous/missing sources, same-file prop aliases, unsupported types, unavailable metadata, preserved contract/classProps identity, source-only calls, supplied-source precedence, and cache lifecycle across projects/edits. Include expressions that would throw if executed.

Use local deterministic Nuxt-shaped fixtures in normal tests for prepared auto-import mappings, application-local overrides, missing/malformed artifacts, explicit fallback/override mappings, and `ui` prop findings. Extend and run the existing pinned `pnpm smoke:nuxt` integration for actual Nuxt UI components alongside generated application CSS; keep its network-dependent scope separate from routine checks and record versions/results. Reuse existing infrastructure instead of adding an application or duplicate harness.

Run `pnpm check` and `git diff --check`. Record focused red/green results, compatibility checks, independent review, and limitations before marking done. A declared mandatory integration check that cannot run must be recorded as incomplete rather than silently treated as passed.
